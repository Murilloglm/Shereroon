## PostgreSQL de produção — leitura somente

Foi utilizada a conexão já autorizada nesta sessão. As consultas rodaram dentro de `BEGIN READ ONLY`, com limite de cinco segundos por instrução e `ROLLBACK` ao terminar. Não foram lidos perfis, senhas, mensagens, identificadores de pessoas, imagens ou conteúdo de arquivos; somente metadados, contagens agregadas e planos de consultas para um identificador sentinela inexistente.

- Versão de schema aplicada: **8**.
- Índices existentes: `messages_channel(channel_id, id DESC)`, `dm_messages_dm(dm_id, id DESC)`, `sessions_pkey`, `sessions_user`, `user_media_pkey` e `user_media_user`.
- Fotos de perfil têm referência em `users.avatar`; o conteúdo reside em `user_media.data`, coluna PostgreSQL `BYTEA`. Portanto, o armazenamento existente das fotos não depende do disco efêmero do Render.
- A amostra é pequena e não constitui teste de carga. O PostgreSQL escolheu varredura sequencial para a tabela pequena de mensagens e um índice para as mensagens privadas; a escolha por varredura pequena não demonstra um gargalo ou índice ausente.

| Medição | Tempo |
|---|---:|
| Abrir conexão PostgreSQL com TLS | 953 ms |
| Ida e volta das consultas pela conexão aberta | 144–149 ms |
| Execução no servidor: consulta de histórico de canal sem resultados | 0,044 ms |
| Execução no servidor: consulta de histórico privado sem resultados | 0,050 ms |

Os planos usaram `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` com `LIMIT 50` e um identificador sentinela inexistente. Não se deve extrapolar esses tempos para uma sala real ou para produção sob carga. Eles mostram, nesta observação, custo de rede muito maior que o tempo de execução dessas consultas pequenas; não comprovam ausência de outros gargalos.

A implementação de idempotência acrescenta a **migração 9**, com identificadores de envio e índices únicos para mensagens de canal e privadas. Ela deve ser validada junto ao código final. O servidor aplica migrações ao iniciar; a confirmação de implantação precisa incluir schema 9. Esta auditoria não aplicou a migração.

## Caminho de publicação disponível

Após concluir correções e validações:

1. Executar `npm.cmd --prefix desktop run release:prepare`, conferir `desktop/package.json` e `desktop/package-lock.json`, e incluir a versão e as alterações autorizadas no commit. A versão prevista é `0.3.4`.
2. Enviar o commit aprovado para `main` sem reescrever histórico. **Não criar/pushar a tag `v0.3.4` manualmente** neste canal: o push manual de tag `v*` aciona o workflow oficial que exige certificado. O workflow de pré-versão cria a tag por conta própria.
3. Rodar `desktop-preview.yml` via `workflow_dispatch` no commit final, usando as URLs HTTPS existentes e notas de release preparadas. `gh workflow run` aceita notas de arquivo com `-F notes=@CAMINHO_DO_ARQUIVO`.
4. Acompanhar o workflow: ele instala dependências com `npm ci`, verifica tipos e testes, instala dependências do desktop, executa seus testes, compila a interface e `ShareRoomAudio.exe`, gera o instalador, assina `latest.yml`, audita assinaturas e calcula os hashes. Só depois publica a pré-versão.
5. Conferir a tag/commit, os seis assets, o campo `cosmicSignature`, a versão do manifesto e os SHA-256 dos bytes publicados. Não sobrescrever assets antigos.
6. Atualizar os links e o tamanho na página de download somente depois de os assets novos estarem disponíveis. O workflow `download-page.yml` publica as mudanças em `download-site/`.
7. Verificar separadamente o backend Render, o schema e a interface pública. Publicar o instalador no GitHub não implanta o backend.

Assets esperados: `CosmicNight-Setup-0.3.4.exe`, `.exe.blockmap`, `.exe.sha256`, `latest.yml`, `SHA256SUMS.txt` e `signature-report.json`.

O build local desta worktree ainda não tinha dependências do desktop nem o helper compilado no início da auditoria. A política PowerShell local consultada era `Restricted`; não foi alterada ou contornada. O runner Windows do workflow é o caminho disponível para o empacotamento.

## Capacidade de deploy do Render nesta sessão

Não foi encontrado token de API ou deploy hook do Render nos nomes de variáveis configuradas dos arquivos locais autorizados, nem CLI Render. A integração Render existe no diretório de plugins, mas a consulta retornou **não instalada**. A inspeção de navegador não foi possível porque o helper nativo de Computer Use estava indisponível, inclusive após a recuperação documentada; nenhuma interação com autenticação foi feita.

Não é possível afirmar que um push em `main` irá ou não acionar autodeploy: essa configuração do serviço não ficou acessível. Se o deploy não acontecer após o push, será necessária a integração Render funcional, uma credencial/deploy hook autorizado ou a ação Manual Deploy no painel para o commit final. Até essa confirmação, o instalador e o backend devem ser reportados como publicações separadas.

Este documento registra observações da auditoria inicial e um procedimento; não declara que a versão 0.3.4 já foi publicada ou implantada.
