## Ordem de execução após a autorização

1. Revalidar a última tag remota e os hashes da 0.3.2. Se houver outra publicação, recalcular a próxima versão antes de continuar.
2. Confirmar backup recuperável do PostgreSQL pelo operador e preservar `DATABASE_URL`, `APP_SECRET` e demais segredos no ambiente do Render. O backup e sua restauração não foram executados nesta preparação.
3. No ambiente seguro com `DATABASE_URL` já injetada, executar `NODE_ENV=production node server/scripts/preflight-production.ts --expect-schema=6`. Não carregar nem publicar `.env.local`.
4. Publicar somente o commit revisado da branch preparada. Um push para `main` dispara a publicação web já configurada e pode acionar o auto-deploy do Render; por isso nenhum push foi feito durante a preparação.
5. O backend aplica a migração 7 na inicialização. Verificar logs e executar `NODE_ENV=production node server/scripts/preflight-production.ts --after-deploy --expect-schema=7`. Não executar o bootstrap se houver migração pendente ou erro de deploy.
6. Inicializar a conta Mg pelo procedimento abaixo e cadastrar o autenticador. As operações globais continuam bloqueadas até MFA válido.
7. Fazer a verificação funcional de produção com contas de teste autorizadas: login, MFA, resgate, presente, rejeição de duplicado, acesso negado a conta comum e entrada administrativa auditada. Não usar mensagens privadas de terceiros na verificação.
8. Publicar os assets novos como **v0.3.3**, no mesmo canal de pré-versão da 0.3.2, com as notas de `0.3.3-notes.md`. Nunca reaproveitar `v0.3.2`, sobrescrever assets ou utilizar `--clobber`.

## Inicialização segura de Mg em produção

O ID local de Mg não é transportado para o banco de produção. A conta de produção recebe um ID aleatório próprio, que será persistido em `global_permissions` e usado em todos os logins.

No shell do backend com o código 0.3.3, `NODE_ENV=production` e `DATABASE_URL` já fornecida pelo ambiente seguro:

```sh
node server/scripts/bootstrap-admin.ts --lookup Mg
node server/scripts/bootstrap-admin.ts --create-mg
```

A consulta inicial é somente leitura. Se retornar vazio, o segundo comando solicita a senha sem exibi-la, cria a conta, mostra o ID gerado e pede a confirmação desse ID em terminal interativo. **Não inserir a senha na linha de comando, no histórico, nas notas de versão ou no repositório.**

Se a conta passar a existir antes da execução, não recriá-la nem redefinir sua senha: conferir a propriedade e usar `COSMIC_BOOTSTRAP_USER_ID` com seu ID real e a senha atual. O bootstrap valida o hash da senha e recusa uma segunda inicialização.

Se o Render não oferecer shell interativo, o operador pode executar a CLI a partir de um ambiente administrativo confiável. Injete a senha autorizada apenas no processo, por gerenciador de segredos, em `COSMIC_BOOTSTRAP_PASSWORD`; para criação sem terminal em produção, a CLI também exige `COSMIC_BOOTSTRAP_CONFIRM_CREATE=Mg`. Para promover conta existente sem terminal, exige `COSMIC_BOOTSTRAP_CONFIRM_ID` igual ao ID verificado. Limpe as variáveis temporárias ao concluir. A senha não é impressa e só o hash scrypt entra no banco.

Depois, entrar como Mg e abrir **Configurações → Administração Cosmic** para cadastrar TOTP e guardar os códigos de recuperação. Não usar SQL para preencher `admin_verified_until`, não desabilitar MFA e não armazenar o segredo do autenticador no pacote. As novas sessões precisam de nova confirmação multifator; a verificação não se transfere entre aparelhos.

O bootstrap não retorna sessão autenticada; nenhuma credencial administrativa entra no build web ou Windows. A recuperação continua documentada em `docs/cosmic-admin.md`.

## Validação e limitações

Resultados consolidados em `0.3.3-validation.json`. Tipos, build web, compilação do helper, empacotamento NSIS, hashes, assinatura Ed25519, fuses e configuração do pacote foram verificados. A auditoria das dependências de produção não encontrou alertas; existem alertas herdados nas ferramentas de desenvolvimento/build. Nenhuma atualização de dependência ou funcionalidade Neon foi misturada nesta versão.

O relatório de hashes dos assets preparados é `0.3.3-artifacts.json`. Se o instalador for reconstruído no GitHub Actions, seus hashes podem mudar; nesse caso devem ser gerados novamente pelo workflow, sempre para v0.3.3 e nunca para v0.3.2.

A preparação valida o SQL em PGlite e inspeciona o PostgreSQL real somente em leitura. A aplicação real da migração, o backup, o cadastro de Mg e o MFA de produção serão executados na sequência autorizada, não antecipadamente.

## Recuperação de deploy

Se o novo backend não ficar saudável, interromper a publicação Windows. A migração é aditiva, portanto o código anterior pode ser restaurado mantendo as tabelas novas. Não apagar histórico, reverter lançamentos de pontos manualmente nem remover a migração aplicada. Se houver transações reais desde o deploy, reconciliar o histórico antes de restaurar um backup; a restauração pode descartar essas operações. Manter a 0.3.2 intacta como referência e registrar as ações do operador.
